# Run the FoundationScale examples on 2 GPUs of an A100-80GB node

This is the entry page for the A100 flavor of the FoundationScale example set: one **shared**
8x A100-SXM4-80GB node, **2 GPUs per run**, no scheduler, all commands runnable from the repo root
(`cd "$FS_ROOT"`). Every workload below beats its own base number; every number is **MEASURED**
(2026-10-12, 2x A100-SXM4-80GB) unless it is labelled **UNMEASURED** or "H200 reference". Peak GB/GPU
is the single highest 5-second `nvidia-smi` sample during each run; `s/step` is `train_runtime/500`
except where noted.

Chapters: [`./llm-2xA100/`](./llm-2xA100/) (Qwen2.5-7B LoRA),
[`./speech-2xA100/`](./speech-2xA100/) (ASR full fine-tunes),
[`./vlm-2xA100/`](./vlm-2xA100/) (MoE VLM, image-only, 16K).
The 2x H200 originals these are derived from live next to them:
[`./speech-2xH200/`](./speech-2xH200/), [`./vlm-2xH200/`](./vlm-2xH200/).

## Hardware and driver notes

| item | fact |
|---|---|
| card | A100-SXM4-80GB = **sm80**, 80 GB. bf16 yes. |
| sanity matmul | warm bf16 8192^3 = **257 TFLOPS** on one card = 82% of the 312 TFLOPS datasheet dense-bf16 peak (**MEASURED**) |
| what does **not** exist here | FP8, FlashAttention-3, NVFP4 (Ada/Hopper/Blackwell paths) → the examples run **`sdpa`** on this box |
| torch build | `cu129` and `cu132` both fine on driver >= 580. This box: driver **580.95.05 / CUDA 13.0**, Ubuntu 24.04, x86_64. We verify `torch 2.13.0+cu129`; on sm80 there is no FP8/FA3 path in either build, so don't chase `cu132` for speed |
| memory | 80 GB per GPU vs the H200's 141 GB: everything measured here fits; the speech rows that do not yet are the ones whose H200 peaks were 82.0/86.2/92.9 GB |
| node | one shared 8x A100 node; other tenants run on other GPUs |
| launcher | no scheduler. Profile `local-single-node` (scheduler `local`); its `node_pattern` only feeds the MASTER_ADDR lint, so it runs fine on any hostname |

### A. Fresh env

The install is `examples/vlm-2xH200/install/requirements-vlm.txt` **minus its three torch lines**
(the `--extra-index-url` cu132 line, `torch`, `torchvision`), with a constraints file pinning the
torch/torchvision you already put in.

```bash
cd "$FS_ROOT"
python3.12 -m venv .venv && source .venv/bin/activate
python -m pip install -U pip

# torch/torchvision first: the same extra-index line already inside
# examples/vlm-2xH200/install/requirements-vlm.txt, with cu132 swapped for cu129 in its URL
TORCH_IDX="$(grep -- '--extra-index-url' examples/vlm-2xH200/install/requirements-vlm.txt | sed 's/cu132/cu129/')"
pip install "torch==2.13.0" torchvision $TORCH_IDX
```

Check it worked: `python -c "import torch, torchvision; print(torch.__version__)"` prints
`2.13.0+cu129`.

```bash
# constraints file pinning exactly what is installed now
python - <<'PY' > constraints-a100.txt
import torch, torchvision
print("torch==%s" % torch.__version__.split("+")[0])
print("torchvision==%s" % torchvision.__version__.split("+")[0])
PY

# requirements minus the three torch lines (^torch matches torch and torchvision)
grep -v -e '--extra-index-url' -e '^torch' examples/vlm-2xH200/install/requirements-vlm.txt > requirements-a100.txt

Check it worked (silent = good):

```

Clean up `constraints-a100.txt` / `requirements-a100.txt` when you are done, or leave them — they

### B. Slow index: offline wheel path

From this node we saw ~20–200 KB/s to PyPI/PyTorch. Do the metadata work on the node and the
bulk download anywhere with a fast index (**MEASURED**: 21 wheels, 152 MB).

```bash
# 1. on the node: metadata only
pip install --dry-run --report report.json -c constraints-a100.txt -r requirements-a100.txt

# 2. list the wheels it wants
python - <<'PY' > wheels.txt
import json
for item in json.load(open("report.json"))["install"]:
    print(item["download_info"]["url"])
PY
wc -l wheels.txt     # 21 lines here; whole set is ~152 MB
```

```bash
# 3. on any machine with a fast index: fetch and copy WHEELS/ back
mkdir -p WHEELS && wget -i wheels.txt -P WHEELS
```

```bash
# 4. back on the node, install fully offline
pip install --no-index --no-build-isolation --find-links WHEELS -c constraints-a100.txt -r requirements-a100.txt
pip install --no-index --no-build-isolation --find-links WHEELS -e ".[train]" librosa "scipy>=1.16"
```

### C. Reusing an existing env: remove the stale packages first

We cloned one that already had `torch 2.13` and hit both traps below on the first import.

| stale package | exact symptom | cause |
|---|---|---|
| `deepspeed 0.14.0` | `import` failure naming `torch.distributed.elastic.agent.server.api`; then `transformers`' `Trainer` refuses to import; FoundationScale ends REFUSE, **exit 96**, naming that module | it imports `log` from a module that torch 2.13 deleted |
| `bitsandbytes` | `ModuleNotFoundError` for `triton.ops` while **peft** wraps adapters (symptom appears at adapter setup, not at import) | `triton.ops` is gone in triton 3.x |

```bash
pip uninstall -y deepspeed bitsandbytes
pip check
python -c "import peft, transformers.trainer, liger_kernel"
```

## Environment variables

`$SCRATCH` = any big filesystem (the caches and temp are large, don't put them on a small home).

| var | value | why |
|---|---|---|
| `HF_HOME` | `$SCRATCH/hf-cache` | model/dataset cache on a big filesystem |
| `PIP_CACHE_DIR` | `$SCRATCH/pip-cache` | wheel cache on a big filesystem |
| `TMPDIR` | `$SCRATCH/tmp` | temp on a big filesystem |
| `PYTORCH_CUDA_ALLOC_CONF` | `expandable_segments:True` | allocator headroom |
| `FS_DEVICE_PEAK_TFLOPS` | `312` | FoundationScale has **no default device peak** — without this the MFU columns stay blank |
| `FS_DEVICE_PEAK_SOURCE` | `"NVIDIA A100-SXM4-80GB datasheet, dense bf16"` | printed alongside MFU |

```bash
export PIP_CACHE_DIR=${SCRATCH:?set SCRATCH to a big filesystem}/pip-cache
export HF_HOME="$SCRATCH/hf-cache"
export TMPDIR="$SCRATCH/tmp"
export PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
export FS_DEVICE_PEAK_TFLOPS=312
export FS_DEVICE_PEAK_SOURCE="NVIDIA A100-SXM4-80GB datasheet, dense bf16"
```

Check it worked: `run_manifest.json` -> `telemetry.perf_device_peak_tflops` is 312.0 and `telemetry.perf_mfu`
holds a value or a named reason (**MEASURED**): Qwen2.5-7B LoRA 0.316; parakeet `UNMEASURED` (no FlopsModel
declared); gemma-4-26B-A4B `UNMEASURED` (MoE experts-per-token not stated, #529). whisper-large-v3 reports
93.98, which is impossible (MFU cannot exceed 1): do not trust MFU for encoder-decoder audio models yet.
The warm-matmul sanity (257 TFLOPS, 82% of 312) is the ceiling a training step can approach, not a target.

## Shared-node GPU hygiene

- This node is shared (8 cards; other tenants' jobs run on the other GPUs). OOM or a slow run is
  often a neighbor, not your config.
- **Pin the GPUs**: `export CUDA_VISIBLE_DEVICES=<gpu ids>` before every launch. All MEASURED runs
  above used exactly one fixed pair.
- **tmux** for anything longer than a smoke test.
- Behind an `http_proxy`, `curl` will send even localhost traffic through it and hang:
  `curl --noproxy '*' http://localhost:<port>/...`
- Abort guard — copy as `launch-guard.sh`, run before every launch (our runs abort if a target GPU
  holds >500 MiB):

```bash
#!/usr/bin/env bash
# launch-guard.sh — refuse to launch if our GPUs already hold someone's job
set -euo pipefail
: "${CUDA_VISIBLE_DEVICES:?pin a pair first: export CUDA_VISIBLE_DEVICES=<gpu ids>}"
for i in ${CUDA_VISIBLE_DEVICES//,/ }; do
  used=$(nvidia-smi --id="$i" --query-gpu=memory.used --format=csv,noheader,nounits)
  [ "$used" -le 500 ] || { echo "ABORT: GPU $i holds ${used} MiB (>500 MiB)"; exit 1; }
done
nvidia-smi --query-compute-apps=pid,used_memory --format=csv   # what is actually on the card
```

Check it worked: the guard prints the compute-app table and exits 0. Peak-memory numbers throughout
this repo mean "highest 5 s `nvidia-smi --query-gpu=... -l 5` sample during the run" — same semantics
as the H200 READMEs.
