# Deliverable 4: Feature Evaluation — Keep / Simplify / Redesign / Remove / Missing

**Scope of evidence.** Every classification below is anchored in the measured census (122,683 git-tracked .py/.sh/.md lines repo-wide; `src/` = 18,915 LOC across 25 files) and the 107 adversarially verified findings (54 CONFIRMED, 53 PARTLY_TRUE, 0 surviving refutations). Where a finding was PARTLY_TRUE, the **corrected form** governs. Three components — the bash launchers (10,171 + 4,986 .sh LOC), the `validation_campaigns/h100_validation/` harness (31,313 .py LOC), and the test suite (29,572 .py LOC) — have **no direct findings**; their classifications rest on the census plus the standing user constraint ("preserve what works on H100 and GB200"), and are flagged as such.

**The load-bearing fact.** The shipped package implements **zero training primitives**: across all 25 git-tracked `src/*.py`, the probe finds `nn.Module` in 0 files, optimizer step in 0, backward in 0, dataloader in 0, forward pass in 0, dist collectives in 0, module-scope torch import in 0 (census §3). **That zero does not mean the package cannot train.** `src/foundationscale/train/` (1,305 lines) builds a `transformers.Trainer`, calls `trainer.train()` and `trainer.save_model()`, and gates each save — importing torch at function scope, which is exactly why every primitive marker reads 0 (#223, #245). The `checkpoint` subpackage is still readers-only; the *save* path lives in `train/loop.py` and in `transformers`. So the asymmetry the table below reflects is not "no trainer exists" but: the verification plane is broad, measured and well tested, while the one training path the package owns is single-backend (`transformers`, not the Megatron/NeMo estate the launchers drive) and the least-covered module in the tree (62%, #228).

These components encode measured incident fixes (aliased-expert byte identity, vacuous-truth refusals, tri-state probes) whose value is in their *semantics*, not their current location. The user's constraint cuts decisively here: nothing in this section gets redesigned for aesthetics. Where a Keep finding was PARTLY_TRUE, the corrected form is what we keep — e.g., the gate-kernel contract is kept even though its downgrade bodies were not evidenced at the cited citations, and `count_census_modules`' purity contract is kept on its documented-docstring strength, not on an unverified regex.

## REDESIGN

**Rationale.** Redesign here means *boundary moves, not behavior changes*. The dominant pattern, confirmed across the T2 series, was that the production decision plane lived in `tools/` scripts while the package imported nothing of consequence from them. **The largest instance of this has since been repaired** (see item 1 below): the adjudication plane now lives in the package. The pattern itself is not fully retired — the compatibility shim still re-exports 63 underscore-private names with F401 "drift tripwires", and the emitter and probe are still script-resident. ## MISSING

**Rationale.** This is the section the review exists for. The findings' category vocabulary puts 20+ entries under Missing, and the census sharpens the shape of the hole: across 18,915 lines of shipped package, the training-*primitive* probe finds **zero** of `nn.Module`, optimizer step, backward, dataloader, forward pass, or a distributed collective (census §3), and four files import torch — the two DCP readers, the parity comparator, and `train/loop.py`.

**Read carefully, that zero is a statement about *ownership*, not about capability.** `train/loop.py` does train; it rents the step loop from `transformers.Trainer` and imports torch lazily, which is exactly why the primitive markers read 0 (#223, #245). So the Missing list below is not "there is no trainer" — it is a list of everything the *one* shipped trainer does not reach:

- one backend, `transformers`, on one topology — no parallelism engine consumes the topology validator, and the H100/GB200 workloads run a Megatron/NeMo trainer the package neither builds nor gates;
- one lifecycle point — the save seam is live in `train/loop.py`, but `STEP_ZERO`, `LAUNCH`, `EXPORT` and `PROMOTE` have no in-process caller, and the public helper for wiring them (`run_event`) still has **0** production call sites (B_gate_engine#4);
- one workload shape — causal-LM SFT; no RL loop, no multimodal path, no recipe registry;
- and the least test coverage in the tree: 62% against a ≥81% package floor (#228).

README's own Quickstart (F1_docs#0, corrected form) still runs pytest, gate controls, and mutation checks — a training framework whose first-run never touches a model, dataset, or GPU even though a console script now exists that would. Per the standing rule, every item below is **EXPRESSIBLE, UNMEASURED** unless a measured run is cited: the design docs describe interfaces (B2's `ExecutionBackend`, B1 §12 recipes) that the census confirms exist in **zero** source files. The governing principle orders the build: easy to use → easy to customize → easy to scale, which is exactly the order of M1→M15.

### M0. The training framework itself
- **A trainer.** No `train.py`, no `train*.py` under `src/` (F1_docs#2, census-verified), no loop, no model construction, no optimizer, no loss. The thinnest honest path per A_front_door#0's proposal: a `foundationscale train`-style entry (or ~20-line example) that builds a `Topology`, validates against a `ClusterProfile`, launches HF Trainer DDP on 8 GPUs with the save-gate wired as a Trainer callback. Migration: **Easy** to start — deliberately thin, because the gate plane is the differentiator and the loop should ride on a maintained backend. This satisfies "model-agnostic architecture, model specifics isolated" only if the model layer is an adapter interface from day one (see M5).
- **A checkpoint *writer*.** The package contains readers (`dcp.py`, `dcp_meta.py`) and a comparator (`parity.py`) — nothing that produces a DCP checkpoint. Save-side gating without a save path is a verification plane orbiting an absent planet.
- **A data plane**: no dataloader, sampler, packing, or tokenization code anywhere in scope (census §3). EXPRESSIBLE, UNMEASURED. Provision via HF datasets integration first, matching the thin-path choice in M0's trainer.

### M1. Trainer-facing gate seam
B_gate_engine#4: the engine has no integration seam into an actual trainer. Build `GateHooks`/`emit(event, **contexts)` in-package (owns REGISTRY/run_event, builds typed contexts like checkpoint-ctx-from-save-path, raises `GateBlocked`). Medium. **Ordering note:** this is the cheapest Missing item and turns FIRST_SAVE/SAVE from dead vocabulary into a contract real trainers can satisfy; land it with M0's thin path, not after.

### M2. Resume/load-side verification
D_checkpoint_verify#0 (census-verified corrected form): no RESUME/LOAD/BEFORE_LOAD/RESTORE member exists in Lifecycle at all; all verification is save-side. Add a resume-side gate that opens the target with `open_weights`, asserts non-empty keys, reads metadata, verifies manifest/step binding, and spot-reads N chunks per shard before `dcp.load`. Hard — depends on M5/M7. Note for launchers: until this exists, "reliable resume" is claim, and nothing in the repo measures it.
