# Self-audit

**What this file is:** the public record of this repository auditing itself by its own doctrine, and a working plan for what has to change before the framework's claims and its evidence match. The nine BLOCKERs in §3 have been fixed (§3.10); the other 849 findings have not. Where an acceptance criterion is quoted below BLOCKER severity, it is still a test that fails on the current tree.

---

## 1. What this is

This repository is a verification framework for large-scale training assets: a gate contract and registry (`gates/core.py`); ten shipped gates over checkpoints, expert aliasing, and training objectives; checkpoint readers for DCP and safetensors (`checkpoint/dcp.py`, `checkpoint/dcp_meta.py`); a streaming weight comparator (`verify/parity.py`); a provenance manifest store (`provenance/manifest.py`); a topology validator (`topology.py`); and the meta-machinery that is supposed to keep all of that honest — a controls harness that replays MUST_FIRE / MUST_PASS fixtures through every gate, and a mutation battery that proves the test suite would notice a broken detector.

The framework's public thesis is that **a check which cannot fail is not evidence**. Its working doctrines, as written in its own audit header, are: zero examined units is never a pass (`all([])` is the founding failure shape); an unqualified count is not a fact — every claim carries a denominator; every detector ships controls that provably fire on the defect and pass on the healthy world; missing denominators must block, not pass; and a claim broader than its evidence is a defect. This audit applied exactly those rules to the repository itself — source, tests, tools, CI, packaging, and README.

It did not come out clean. The process produced **858 accepted findings — 9 BLOCKER, 304 MAJOR, 545 MINOR — plus 49 structural blind-spot classes** that the finding process, by construction, could not see from inside. The most uncomfortable result is not any single defect; it is that the framework's own dispatcher, its own test battery, and its own public claims each reproduce, at one remove, the failure the project exists to prevent: green signals that no verified work stands behind.

---

## 2. Method

The finding set was produced in three rounds, and the reason to take it seriously is the second one.

**Round 1 — generation.** 26 agents (11 per-module passes, 8 whole-tree lens passes, 7 test/meta passes) produced 795 findings. The entry bar per finding was mechanical: an anchor (`file.py:line`), a falsifiable claim, and an acceptance criterion written as the test that fails today.

**Round 2 — adversarial verification.** 38 verifiers were each handed the *full source of one file* plus every finding anchored to it, and instructed to refute by default. Of the 795: 704 were CONFIRMED, 56 were IMPRECISE and survive only as corrected by the verifier, and 35 were REFUTED and removed. 8 domain designers, working cross-module, added 375 findings that module-local passes structurally miss.

**Round 3 — synthesis and completeness.** 24 synthesisers merged duplicates, corrected severities, and made acceptance criteria executable. The 1,135 surviving items consolidated to **858**. 4 completeness critics were then given the entire surviving set plus the whole-tree API surface and asked a different question — *what classes of problem can this audit not see?* — producing the 49 structural gap classes in §6.

Final shape of the backlog: by severity 9 BLOCKER / 304 MAJOR / 545 MINOR. By kind: 312 weaknesses, 133 features needed, 234 tests needed, 179 refinements. By estimated effort: 612 small, 225 medium, 19 large. 855 of the 858 items carry an acceptance criterion written as the test that fails today; the 3 that do not say so explicitly.

**What this method does not establish:**

- **Completeness.** The completeness critics found 49 classes of blind spot *after* three rounds. §6 is, by construction, a partial list of what is missing.
- **Behavior on real artifacts.** The audit reviewed code and tests. The checkpoint fixtures remain synthetic. Since the audit, two real production checkpoints have been adjudicated outside CI — the framework abstained and blocked on both (see §4) — but no gate has yet run against a real checkpoint in CI, and none has fired on a real defect anywhere.
- **The repository's headline metrics.** The audit consumed the repo's self-reported counts (tests, coverage, mutation score) as ground truth. That is itself a finding; see §6.
- **That the backlog is perfectly formed.** The consolidated ledger retains known duplicate *filings* — the same defect entered twice from two vantage points — documented by the critics and by backlog finding G-product-14. The merge work is listed in §6 and phased in §7. One integrity defect has since been fixed rather than merely logged, and it is worth stating plainly because it is the same class this document is about: **the ledger presented 858 findings under 485 distinct IDs.** 24 synthesisers each numbered from 1 inside their own domain, and the merge concatenated without re-keying, so 275 rows silently shared an ID with another row. An ID advertised as a key that is not one is an ID-as-key defect, and it did real damage before it was caught — a batch of fix agents was briefed off `{item["id"]: item}`, which keeps the last colliding row, and every one of them fixed a different defect than the one it was assigned. The ledger has been re-keyed to 858 unique IDs, each row retains its `legacy_id`, and every citation in this document was re-pointed per occurrence. The audit committed the defect the audit exists to find; the counts above were never affected.
- **That fixes compose.** The nine BLOCKERs in §3 have landed and the tree is green (§3.10). Nothing below BLOCKER has been touched, and every acceptance criterion in §5 remains a statement about the current tree.

## 3. The nine BLOCKERs

Each subsection: what it was, where, the concrete bad outcome, and the acceptance criterion that closes it. We lead with the one that is the framework's own thesis, violated in its own dispatcher.

**All nine have since been fixed.** The diagnoses below are preserved in the present tense as they were written against the pre-fix tree, because the diagnosis is the part worth reading — the defect classes recur. §3.10 records what landed, what is pinned, and what was deliberately left open. Where a subsection says "today", read "before the fix".

### 3.1 Zero-work sweeps return green at every layer — `W-gatecore-1`

**What it is.** `GateRegistry.run` on an event with no registered gates returns a `GateReport` whose `ok` is `True` (`gates/core.py:561-587`); `verify_controls` returns success when it targeted zero gates — empty registry, or an explicit `gate_ids=[]`; and the CLI prints success accordingly. The current test suite pins this behavior rather than prohibiting it. The core suite's own charter — "if any of those paths ever yields success again, this suite … must be where it is discovered" — stands opposite a test that pins the opposite outcome.

**Why this is first.** The founding incident was an `all([])` silently read as success. The framework that exists to make that impossible implements it at the registry, the report, the controls verifier, and the controls CLI — all four layers at once. A launcher that sweeps an event nothing registered for is told *all clear*.

**Acceptance.** `test_empty_event_sweep_is_blocking_vacuous`: a fresh `GateRegistry().run(Lifecycle.SAVE, object())` must return `not report.ok` and `report.is_vacuous`, with exactly one synthesized result at `Verdict.VACUOUS` and `Coverage.none("gates")`; negative control — one passing SAVE gate — returns `report.ok`. Fails on today's tree.

### 3.2 The byte-volume gate prices declared shapes, not stored bytes — `W-ckpt-1`

**What it is.** `ExpertByteVolumeGate` sums `prod(shape) × _DTYPE_BYTES` per FQN (`gates/checkpoint_gates.py:103-105`): metadata-implied bytes, not physical storage. The distinctness gate's fallback (`storages = {t.storage_id if t.storage_id is not None else t.fqn …}`) reads 128 unique-FQN aliases as 128 "distinct storages", and its PASS string (`gates/checkpoint_gates.py:313-317`) still asserts that every shard group owns its storage.

**Bad outcome.** The count-correct aliased variant of the founding incident — 128 FQNs present, every shape right, every dtype right, one physical tensor behind them — scores byte ratio **1.000** and earns a distinctness PASS whose detail asserts the thing that is false. The two gates shipped as the incident's detectors are, for this variant, exactly as blind as the estate's original checks.

**Acceptance.** `test_byte_gate_prices_distinct_storage()`: a context of 128 correctly-shaped expert FQNs all sharing `storage_id="S"`, with `expected_expert_bytes=128×shape_bytes`, must produce an `expert_bytes` FAIL whose detail names distinct-storage bytes. Today: PASS, ratio 1.000. A companion test pins that the distinctness claim degrades honestly when `storage_id` is absent.

### 3.3 The denominators come from manifest fields nothing produces — `F-ckpt-1`

**What it is.** Every denominator the checkpoint gates adjudicate — `declared_fqns`, `num_experts`, `num_moe_layers`, `expected_expert_bytes` — is read via `getattr` from manifest attributes (`gates/checkpoint_gates.py:155-161`) that no shipped code writes.

**Bad outcome.** Every real first save lands in SKIP/VACUOUS, and the founding incident is uncatchable outside synthetic fixtures. This is important enough that §4 is devoted to what it means for adopters.

**Acceptance.** `test_declared_block_round_trip_and_wiring()`: a `DeclaredCheckpoint` dataclass (`num_experts` / `num_moe_layers` / `expected_expert_bytes` optional ints; `declared_fqns` a tuple made sorted-unique in `__post_init__`; `naming_convention`; `expert_weight_pattern` required iff `"custom"`), serialized through the manifest, loaded through the real discovery path, and consumed by `from_path` — round-tripped end to end, not handed to the gates by a test.

### 3.4 NaN payloads launder a comparison into `CLOSE` with `max_abs_diff=0.0` — `W-io-1`

**What it is.** A single NaN on either side of `compare_keys` (`checkpoint/dcp.py:1140-1183`) yields the pass-grade verdict: `torch.equal` makes the pair non-bitwise; `diff.max()` propagates NaN but CPython `max(0.0, nan)` keeps `max_abs == 0.0`; and the NaN-poisoned sum-of-squares makes `cosine=None`, which satisfies the `cosine is None or cosine > close_min_cosine` arm of the CLOSE condition.

**Bad outcome.** The comparator behind the export-verification story returns its *cleanest-looking* verdict — pass-grade, zero max difference — on poisoned payloads. The non-finite laundering class has sibling instances in the parity gate (`W-par-2`, `W-par-3`, MAJOR).

**Acceptance.** `tests/test_compare_keys_nonfinite.py::test_nan_never_close` over real in-memory `WeightSource` implementations: NaN-left-only, NaN-on-both-sides-same-positions, and NaN-plus-large-finite-divergence must each return a verdict outside `{"CLOSE", "EXACT"}` with `max_abs_diff != 0.0`.

### 3.5 Git capture inherits the caller's environment: the probed repository and the hashed diff are malleable — `W-prov-1`

**What it is.** `_git` / `_git_bytes` call `subprocess.run(["git", "-C", root, …])` with no `env=` (`provenance/manifest.py`, git helpers from :604). Git's own documentation states `GIT_DIR` / `GIT_WORK_TREE` / `GIT_CONFIG_PARAMETERS` override repository discovery — `-C` only changes the working directory — and `git diff --binary HEAD` honours external diff drivers and textconv filters.

**Bad outcome.** A poisoned launcher records repository A's revision and a driver-filtered diff while running repository B's code. The "what code ran" record — the foundation of the provenance plane — can describe a different repository than the one that executed, with every downstream rollup reporting CLEAN.

**Acceptance.** `test_git_env_cannot_redirect_probe`: run capture in a real subprocess with `GIT_DIR` / `GIT_WORK_TREE` pointing at decoy repo A and `root` at repo B; assert the recorded commit is B's HEAD. Today it returns A's.

### 3.6 The manifest load boundary is fail-closed at version granularity, fail-open at field granularity — `W-prov-2`

**What it is.** `load()` refuses unless `schema_version == 1` — an exact-equality check that JSON `true` and `1.0` slip past, only to die later in `_expect_int` as a generic `ManifestError` (a taxonomy accident) — while every `from_dict` constructs from a fixed known-key set with no unknown-field check (`provenance/manifest.py:92` and the `from_dict` family).

**Bad outcome.** Any field added by a newer writer is silently dropped by an older reader with no signal. The store that exists to keep run history honest will edit that history on read — and, as a second finding notes, with no record of which tool wrote a manifest (`W-prov-20` in the store majors), capture-bug errata can never be scoped retrospectively.

**Acceptance.** `test_schema_version_acceptance_matrix` parametrized over `{1 (loads), 0, -1, "1", 1.0, true, <absent>}`: each refusal must arrive as `ManifestVersionError` carrying `found` / `supported`, via the version path, not a downstream type error; unknown fields on load must be surfaced, not silently discarded.

### 3.7 No API can run an event whose gates take different contexts — `F-gatecore-1`

**What it is.** The registry broadcasts a single context object, unchanged, to every gate of an event (`gates/core.py:564-587`). No gate declares what it accepts. Every integrator must hand-rebuild fan-out, timing, error conversion, and report aggregation — and get it wrong opaquely: a full-registry FIRST_SAVE/SAVE sweep is permanently ERROR because incompatible context families collide (`W-gatecore-15`).

**Bad outcome.** The trainer-agnostic adapter spine — the first thing every adopter needs — does not exist. Wiring requirements are undiscoverable, and the failure mode for miswiring is indistinguishable from a gate malfunction.

**Acceptance.** `Gate.context_type: ClassVar` set on all shipped gates; both `_coerce` functions promoted to `Gate.coerce_context(ctx)`; and `run_event(registry, event, contexts: Mapping[type, Any], *, required=(), missing_ctx="block" | "report-skip", …)` with typed fan-out and the specified missing-context semantics.

### 3.8 The mutation battery scores any crash as a kill — `W-metatest-1`

**What it is.** `run_suite` returns `p.returncode == 0`, so the battery's `if green … else killed` branch (`tools/mutate.py:327-343`) maps *every* non-green outcome — `rc=2` collection errors, usage errors, `rc=1` with zero attributed `FAILED` lines — to `[killed]`, counting toward the battery's green exit. A kill is credited on a single run, so one flaky failure is recorded as detection and never re-confirmed. There is no `timeout=`, so a loopy mutant hangs the battery itself.

**Bad outcome.** The public claim that the battery catches its mutants is produced by a scorer that cannot distinguish "a test caught the defect" from "pytest could not start". The artifact that justifies the framework's existence cannot show its work — compounded by the fact that the battery emits no machine-readable report, so the headline tally is maintained by hand (`F-metatest-5`).

**Acceptance.** `tests/test_mutate_classify.py` against `main(argv, suite_runner=fake)`: fake `rc=2` must list the trial under `unscored`, never `killed`, and must not count toward exit 0; `rc=1` with an ERROR-only summary likewise.

### 3.9 The mutation battery's other direction: skip-poisoned greens read as ALIVE — `W-metatest-2`

**What it is.** The ledger carries a second blocker over the same scoring branch (`tools/mutate.py:327-397`): a *green* run whose tests were skipped prints ALIVE — although a mutant whose effect is to skip the suite's tests scores as "survived" for exactly the wrong reason — and the skip guard that would catch this is armed only by an environment the tool itself never sets. We include both filings deliberately: one locus, two directions of misscoring, two different consolidation proposals. They were filed under a single ID and are now `W-metatest-1` and `W-metatest-2`; that consolidation missed them twice is itself the ledger-integrity failure documented in §6 (`G-adversary-9`, `G-product-14`), and we would rather show both in §3 than quietly merge one away.

**Bad outcome.** "42/42 killed" and "mutant survived" are both, today, un-attributed readings of an exit code. Neither direction of the battery's verdict is currently evidence.

**Acceptance.** `tests/test_mutate_scoring.py` over new `SuiteOutcome` / `TrialVerdict` types: a collection-error outcome yields `TrialKind.UNSCORED` with `rc=2` in its reason, never a kill; a zero-attribution `rc=1` is never a kill; greens with skips cannot mint ALIVE.

All nine are closed, in two waves — six first, then the three whose fixes touch files the first wave rewrote. Every acceptance criterion quoted in §3.1–3.9 is now a test in the suite, and each was confirmed to fail on the pre-fix tree before its fix was applied. A baseline run established the tree was green *before* any patch, so every red that appeared during the work was attributable.

**Tree state as of today.** 582 tests pass — 412 before this work began, 500 after the BLOCKER wave, 543 at this document's first revision. `ruff check`, `ruff format --check` and `mypy` are clean. The controls harness imports 5 gate modules, registers 9 gates and replays 42 controls — every gate blocks its own deliberately defective inputs — and prints each registered gate's declared dispatch context type, with an explicit marker where none is declared, stating the ratio as a fact: 4/9 gates typed, 5 on the untyped legacy broadcast path. The mutation battery scores 42 mutants across 6 modules: **42 killed, 0 alive, 0 unscored, 0 not-applicable, 100% caught in every module**, with all 6 modules restored byte-for-byte afterwards — and, this revision, with a negative control beside it: **`MUST-PASS CONTROL: 1/1 exercised inert edit(s) survived`**.

**That last clause is a retraction, and it is the most important paragraph in this section.** The first revision of this document published the same `42 killed … 100% caught in every module` line without it. That figure was produced by a harness that could not tell detection from self-detection, and we can state the defect as a measurement rather than a worry, because we measured it: a deliberately **inert, comment-only** mutant — an edit that changes no behaviour and that a sound suite therefore *cannot* detect — was scored `[killed]`, and the run exited 0 with `caught=100%`.

The mechanism was a coupling nobody had looked for. The meta-tests that verify the battery drove the real `mutate.main(())` against the **live** `tools/mutations.json` and the live tree. So when the outer battery mutated a shipped module, the inner run's anchor into that module no longer matched, the inner run exited 2 on a stale anchor, the meta-test asserting a clean inner exit failed — and the outer battery recorded that failure as a test reacting to the mutation, complete with attribution. The battery was detecting its own footprint. Any mutant that perturbed a file a meta-test's anchor pointed into was killed on contact, regardless of whether it changed behaviour, which means neither the tally nor the per-module `caught=` figure was evidence about the test suite at all.

Two changes close it, and the second is the one that keeps it closed:

- **A `table=` / `module_paths=` injection seam.** Every `main()` call in the meta-tests now runs against a scratch table anchored at files under `tmp_path`. Mutating any shipped module cannot change what those tests measure, so the feedback loop is severed at the source. A test pins the seam itself (`test_injected_table_never_reads_live_table`) — otherwise a future test could quietly reintroduce the live-table read.
- **A MUST-PASS control row in the table.** `must_survive: true` marks a behaviour-preserving edit whose *only* correct outcome is survival. If the suite reports killing it, the attribution machinery is proven unsound and the entire run is voided at exit 2 — ahead of every other finding, because a run that can manufacture kills has nothing to say about the ones it printed. The same inert edit that used to score `[killed]` now reports `[ctrl ok] parity/inert-control-must-pass: no fault, no detection — attribution sound`.

And because doctrine (2) says coverage is a returned fact and never an inference from silence, the control result is printed on **every** run including the empty case: a table configuring zero `must_survive` rows now says so in words, states what it costs, and **exits 2** rather than printing a confident tally with its negative half missing. A control row that is configured but never exercised — a stale anchor, an unscored trial — reads as its own third state rather than collapsing into either "passed" or "not configured". That block sits between UNSCORED and ALIVE in the exit precedence: it is a claim-nothing failure, not an actionable gap.

So the mutation line means something it did not mean before, twice over. §3.8 and §3.9 stopped the battery from reading an exit code as a verdict: it now reruns each mutant to confirm *which* tests reacted, so a crash cannot be banked as a kill and a skip-poisoned green cannot be banked as a survivor. This revision stops it from grading its own homework: the same number is now printed beside a control that proves the grader can still say "no". The number is smaller in claim and larger in evidence, and it took two passes to get there — which is itself the honest headline. The tool whose entire purpose is to catch checks that cannot fail was, until this revision, a check that could not fail. We found it with the doctrine, not in spite of it, and it is the strongest available argument for applying the doctrine to the meta layer first.

**What was deliberately left open.** Each of these is fail-closed and discoverable, not silent:

- **Five of the nine registered gates do not yet declare a `context_type`** — the four in `objective_gates.py` and `ExpertAliasGate` in `example.py`. Reached through the new `run_event`, they produce a blocking "declares no context_type" ERROR rather than running against a context they cannot consume. Their behaviour through the older broadcast path (`GateRegistry.run`) is byte-identical to before. The fix is one class attribute and one `coerce_context` delegation per gate.
- **`WeightParityGate` still requires the caller to pass `expected_keys`.** Clause (d) of `F-ckpt-1` — deriving them from the manifest join — is not implemented; the seam it needs (`CheckpointGateContext.from_path` resolving `manifest.declared`) now exists.
- **`tensors_per_expert_layer` is captured and stored but not consumed** by the coverage denominator, which still assumes two projections per expert. This is correct for the Megatron-style layouts in the fixtures and wrong for HF-style three-projection MoE. Since the selector rewrite this is no longer only a note: `tests/test_expert_layouts.py` runs Mixtral and Qwen contexts through the gates and asserts the resulting `checked=24, expected=16` explicitly. The mismatch is in the strictly-more-examined-than-declared direction, which does not block, so the test's job is to keep the wart visible until the denominator consumes the field.
- **The controls listing now reports the typing it used to hide.** It prints each registered gate's declared dispatch context type, marks explicitly where none is declared, and states the ratio as a fact: 4/9 gates typed, 5 on the untyped legacy broadcast path. The visibility shipped; the typing work for the five is the first bullet of this list.
- **Nothing here closed the real-artifact gap — but §4 no longer describes it the same way.** These fixes were verified against synthetic fixtures and a green suite. Since they landed, two real production checkpoints have been adjudicated (§4): the framework abstained and blocked on both rather than pass what it could not examine. That is the vacuity machinery surviving contact with production bytes, not detection — no gate has yet fired on a real defect, and the real-artifact corpus in Phase 5 of §7 remains the item that can falsify the rest.
- **Two defects found *after* the nine were closed are also fixed, and neither came from the ledger.** The layout-blind expert selector (§4.1) came from pointing the tool at real bytes; the mutation battery's self-detection (retracted above) came from applying the doctrine to the tool that applies the doctrine. Both were invisible to a green suite of 543 tests, and both are the same shape: a check whose denominator was chosen by the thing being checked. We record them here rather than folding them into §3 because the nine were found by reading, and these two were found by measuring — which is the ratio the ledger should be judged on.

## 4. The honest limitation

If you are evaluating this library for adoption, this is the section to read twice.

**Four checkpoint gates have now adjudicated two real checkpoints — and the strongest result is a negative one.** This section previously opened with the sentence "No gate in this repository has ever adjudicated a real checkpoint." That sentence is false as of this week. What replaces it is weaker, and more interesting, than its inversion: nothing has been *detected* on a real artifact, because neither artifact was corrupt. What the two runs established is that the framework abstains correctly on bytes it had never seen — the doctrine surviving contact, not the detectors convicting anything.

*What ran.* A new tool, `tools/real_checkpoint_probe.py`, runs the four shipped checkpoint gates (`checkpoint.expert_distinctness`, `checkpoint.expert_bytes`, `checkpoint.save_complete`, `checkpoint.first_save`) against an on-disk checkpoint, reading tensor-header metadata only — tensor data is never materialised. Its design point is the denominator-provenance doctrine applied to plumbing: the `declared_*` denominators come from an independent source — the HF `config.json` beside the weights — never from the checkpoint being judged, and never from the framework's own run manifest. Exit codes: 0 CLEAR, 1 a blocking verdict was reached, 3 could not measure.

It was pointed at two production checkpoints of a public open-weights model family on a GPU cluster, and both runs completed in well under a second each (0.16 s and 0.17 s) on a login node — header parse only, no GPU, no scheduler job.

- **A dense multimodal instruction-tuned checkpoint.** safetensors; 2,130 tensors, all real, all bfloat16; 15,992,314,836 metadata-implied bytes (14.89 GiB); storage_id coverage 2,130/2,130. The declared expert count is zero, on the stated basis that the config declares no routed-expert count at all — the config's statement, not an inference from the checkpoint.
- **A 128-expert mixture-of-experts checkpoint from the same family.** safetensors; 1,013 tensors, all real, all bfloat16; 51,611,872,412 bytes (48.07 GiB); storage_id coverage 1,013/1,013. The probe's scoped config reader found `num_experts = 128` one level down, in the nested text sub-config, exactly where this family puts it.

| Gate | Dense checkpoint | 128-expert checkpoint |
|---|---|---|
| `checkpoint.expert_distinctness` | SKIP (0 units) — context declares no experts and none are present | VACUOUS — 0 expert tensors examined against 128 declared; therefore proves nothing |
| `checkpoint.expert_bytes` | SKIP (0 units), same reason | VACUOUS — 0 examined; there is nothing to sum |
| `checkpoint.save_complete` | VACUOUS — no run manifest beside the checkpoint, so 0 declared tensors examined, which proves nothing | VACUOUS — same shape |
| `checkpoint.first_save` | FAIL — first save is defective: `checkpoint.save_complete=VACUOUS` | FAIL — names all three |

Both runs exited 1. Neither produced a green.

The strongest single result is a negative one: on the MoE artifact, the framework was handed a config that declares 128 experts, found no expert tensors its selector would recognise (§4.1), and declined to pass a population it could not examine — naming 0 as the number examined and 128 as the denominator it was measured against. That is every doctrine in this document firing at once, on bytes the gates had never seen.

*What changed.* The checkpoint gates adjudicate ratios — examined against declared bytes, declared FQNs, declared expert counts — and until `F-ckpt-1` landed (§3.3) every one of those denominators was read from manifest attributes that nothing in the repository produced. There is now a `DeclaredCheckpoint` block on the manifest, three producers that build one (`declared_from_hf_config`, `declared_from_megatron_args`, `capture_state_dict_keys`), and a `from_path` adapter that resolves it. `test_declared_block_round_trip_and_wiring` carries a declaration through the real manifest and out the other side into a gate verdict, and `test_manifest_without_denominators_yields_none_not_empty_tuple` pins the production regime that `T-ckpt-2` said was untested: an adapter exposing no denominators now yields `None`, which blocks, rather than `()`, which used to auto-satisfy. As of this week, the producers have also met a real `config.json` — and one of them was caught disarming every expert gate on one; see §4.1.

*What did not change.* The suite still stands on fixtures for everything the fixtures test, and the probe runs examined two healthy artifacts of one family — a sample of two, covering one naming grammar and one config shape. Specifically still open:

- The real-file replay of the 87.5% incident, with no stubbed manifest anywhere in the path, does not exist (`T-ckpt-9`).
- The expert-content gate's context takes caller-supplied tensors and fingerprints; the streaming context and the production disk adapter are requested features, not shipped code (`F-ckpt-2`).
- The fixtures remain monocultural — one shard, one tensor, declared metadata derived from the payload embedded in it (`W-metatest-11/12/13`). A fixture that derives the denominator from the artifact it is checking cannot fail the way production fails. §4.1 is that sentence, demonstrated twice.

Three consequences follow, and none should be softened:

1. **On a real artifact the gates abstain rather than misjudge — measured now, not predicted.** This consequence used to be a forecast ("the gates *will* abstain"). It was tested twice this week and held both times: every gate that could not examine anything said so, named 0 as the number it examined, named why, and blocked. But a confirmed prediction of abstention is not the same as a working detector. Abstention is what the framework does when it cannot see, and on the MoE artifact it could not see the expert population at all (§4.1). Since the selector rewrite it *can* see that population — 60 stacked expert tensors, 45,675,970,560 bytes — and it still abstains on per-expert identity, now for the structural reason rather than the buggy one. That is a better abstention, not a detection. Until a gate fires on a real defect, the founding incident remains uncaught in production — no longer for want of plumbing, and no longer for want of a selector, but for want of a demonstrated firing.
2. **Abstention currently satisfies enforcement.** Per `T-gatecore-6`, a `required=` gate that ran and returned SKIP satisfies the requirement today — the ratify-or-forbid decision is unpinned. Do not read "all required gates ran" as "all required gates adjudicated." This one interacts badly with consequence 1 and should be read alongside it.
3. **If you write the producer yourself, the gates will trust your numbers.** Per `W-gatecore-20`, denominators are producer self-reports: a run that declares `num_experts=16` receives a full-coverage `16/16` PASS over the remains of a 128-expert model. The denominator-provenance discipline that would make your producer's claim auditable is backlog, not code — and it is the reason a denominator should come from a source independent of the artifact being judged. The probe holds to that discipline — its denominators come from the config beside the weights, not from the checkpoint and not from the run manifest — and §4.1 shows the discipline was load-bearing: the framework's own producer, applied to a real config, silently classified a 128-expert model as dense.

So, concretely: what is proven is the detector logic, as controls replayed over synthetic reproductions of real incidents — the 128-saved-as-16 aliasing, the empty comparison set, the inert objective — plus a wired path from an independently sourced declaration to a gate verdict, and one new fact: pointed at real production checkpoints, the framework refused, twice, to mint a pass over populations it could not examine. What is not proven is detection. No gate has yet fired on a real defect, and there is no real-artifact MUST_FIRE control: the probe's `--inject-alias` control was requested on both runs and reported `skipped` — there were no expert tensors to rewrite — which the probe now correctly counts as a blocking reason rather than a clear, because the claim it exists to test is unverified on this artifact. Abstention held; detection is untested in production, and a framework that only ever abstains on real inputs has not yet earned the word "gate". The path has now survived contact with two checkpoints written by a real trainer — and what survived is the refusal, not the firing. Adopting today still means adopting an integration problem, now with two demonstrated failure shapes of the kind the fixtures could never teach. The honest way to describe this library: *the detectors from the founding incident, proven alive against reproductions of it, with plumbing that has now met production and abstained exactly where the doctrine says it must — and has never yet convicted a real artifact.* Closing that is the real-artifact corpus in Phase 5 of §7, which remains the item most worth pulling forward, because it is the only one that can falsify the rest.

### 4.1 What two real artifacts exposed that 543 tests had not

Neither defect below existed in any test's world. Both surfaced within the first two real artifacts the framework ever examined, and both are exactly the class a synthetic fixture cannot produce when the fixture is written by the detector's own author — the author has already assumed the layout, so the layout never varies.

**A layout-blind expert selector.** `_expert_weights()` in `src/foundationscale/gates/checkpoint_gates.py` selects the expert population with a single regex, `.*experts.*linear_fc[12]\.weight\d*$`. That matches the per-expert Megatron layout the fixtures were written in. It matches nothing in a stacked HF layout, and nothing in the per-expert HF or Mixtral-style layouts either. On the 128-expert artifact it selected 0 of 1,013 tensors — which is where the VACUOUS verdicts in the table above came from. Measured ground truth on that artifact, by direct enumeration: 90 expert-ish tensors — 60 expert weight tensors plus 30 router tensors — carrying 90 distinct storage_ids and 45,675,970,560 implied expert bytes. The expert weights are stacked: shapes (128, 2816, 704) and (128, 1408, 2816), with the expert index as dimension 0.

The structural consequence matters more than the regex, and it is a finding about what the framework can and cannot ever claim, not merely a bug. In a stacked layout, all 128 experts live in **one tensor at one storage span**, so per-expert aliasing — the exact founding incident, 128 experts saved as 16 — is **not observable from metadata at all**. A per-expert layout makes aliasing visible to a header parse; a stacked one does not, and no amount of regex work changes that. The only honest response on a stacked artifact is a specific, stated abstention — which is what the probe produced. A "fix" that merely taught the selector to find the stacked tensors would graduate the gates from blind to overclaiming: still nothing per-expert to adjudicate, now with a PASS-shaped temptation attached.

**The selector has since been rewritten, and the abstention is now the shipped behaviour rather than an accident of a regex that matched nothing.** `_split_expert_layouts` classifies every expert-named tensor into one of four outcomes, and the verdict follows the outcome rather than the naming:

| Outcome | What it covers | Verdict on a clean artifact |
|---|---|---|
| PER-EXPERT | Megatron shard-suffix and global-index spellings, Mixtral `w{1,2,3}`, Qwen `{gate,up,down}_proj` | real PASS — N names, N spans, aliasing observable |
| STACKED | HF `experts.{down_proj,gate_up_proj}`, Megatron fused `experts.linear_fc*` | **SKIP with a stated reason** — per-expert identity is unobservable, so the gate names what it did examine (leading dims, sibling pricing, whole-span sharing) and declines the rest |
| UNKNOWN | an expert-named tensor matching no family | FAIL, naming the FQN — an unrecognised layout is not a dense model |
| MIXED | both families present in one checkpoint | FAIL — the mixture is the defect; metadata cannot separate a heterogeneous model from a half-converted one, and either reading silently moves the denominators |

Re-run against the same 128-expert artifact's metadata, the selector now takes **60 of 1,013 tensors** and none of the 30 routers — `router.per_expert_scale` contains the substring `expert` but no expert path *segment*, and the selection is segment-exact so the trap is not taken. `checkpoint.expert_distinctness` returns SKIP over `checked=60`, evidence `layout=stacked`, `per_expert_identity=unobservable-from-metadata`; the false stated reason "the checkpoint contains no expert tensors" is gone and is pinned against by name. `checkpoint.expert_bytes`, which *can* price a stacked layout completely, reaches a real non-vacuous PASS on 45,675,970,560 bytes against a manifest-supplied denominator — and FAILs at ratio 0.500 against a deliberately doubled one, because a gate that only ever passes has proven nothing.

So the blindness is closed and the overclaim was not opened: what changed is that a checkpoint the gates previously described falsely, they now describe correctly, including the part they cannot judge. `tests/test_expert_layouts.py` pins all four outcomes with a MUST_FIRE and a MUST_PASS case per family, asserts the router exclusion by name in every fixture, and pins the stacked verdict as SKIP *and* not-PASS *and* not-FAIL — so a later change can neither promote the abstention into a claim nor regress it into a false alarm. One wart is pinned rather than fixed: the coverage denominator still prices two projections per MoE layer, so three-projection families report `checked=24, expected=16` — strictly-more-examined-than-declared, the non-blocking direction, and the test says so out loud rather than rounding it away.

**A nesting-blind config producer.** The second defect is in the manifest producer, not the probe. `declared_from_hf_config` in `src/foundationscale/provenance/manifest.py` reads `num_experts` only from the top level of the config dict. This model family nests it one level down, under the text sub-config — so the framework's shipped producer would classify a 128-expert model as dense, silently disarming every expert gate, on the real config of a public open-weights family. The probe escaped only because it carries its own scope-aware config reader, which searches the nested text scope before the top level; the framework's own shipped producer did not. This has now been fixed: the producer searches the nested scope and records the scope it read the value from as part of the declaration's basis — the provenance the number always needed.

**What this says about the fixture corpus.** The ledger already carried the prediction without being able to demonstrate the cost: fixtures that are monocultural — one shard, one tensor, declared metadata derived from the payload embedded in them (`W-metatest-11/12/13`) — and every MUST_FIRE world authored by the same hand as the detectors (G-design-6). The cost is now demonstrated, twice, in the first contact with real bytes: one naming grammar the fixtures never contained made 45,675,970,560 bytes of expert weights invisible to the gates built to guard them, and one config shape the fixtures never contained made a 128-expert model look dense to the producer built to describe it. Every fixture passed throughout both failures. A corpus written by the author of the detector is a claim about the detector's neighbourhood, not about the world, and Phase 5's externally sourced corpus is the only known antidote.

### gatecore — gate contract, registry & controls runner (156)

The largest area, because the contract layer is where the thesis lives. Beyond the two blockers, four weakness themes dominate. Verdicts are **write-only**: no envelope, no identity, no version, and an unconstrained `evidence` mapping that can kill report serialization at `to_json` time (`gates/core.py:227-265`). The anti-vacuity rule **binds the `ok()` helper, not the result type** — a hand-built `GateResult(PASS, Coverage(checked=0))` flows through untouched. The controls harness **accepts non-detection**: MUST_FIRE is satisfied by VACUOUS or ERROR, MUST_PASS by SKIP (`gates/core.py:667-678`); the walker cannot reach the tenth gate and its banner has no census denominator; `controls()` is invoked twice, so the printed denominator and the executed fixtures come from different generations. The **exception net stops at `Exception`** — `sys.exit(0)` inside a gate exits the launcher green, and a top-level `SystemExit` in a gate module exits the controls runner silently. The feature items are the real integration spine: a shipped per-event required-gate policy (`F-gatecore-3`), the five-line `SaveHook` (`F-gatecore-11`), a durable append-only report store (`F-gatecore-7`), artifact receipts (`F-gatecore-13`), a rank-aware execution helper (`F-gatecore-15`), a common exception root (`F-gatecore-5`), per-control isolation and timeouts (`F-gatecore-16`), consume-side and export-side lifecycle events, and gates that finally adjudicate the manifest plane.

### metatest — verifying the verifier (148)

The machinery that verifies the verifier is the least-verified code in the tree. Beyond the two battery blockers: restore integrity is in-memory plus an `assert` stripped under `-O`, with no reconciliation after an interrupted run (`W-metatest-4`); the green baseline the battery trusts is neither armed nor audited, and non-strict xfail lets a rotting tolerated-failure go quietly XPASS-green (`W-metatest-5`, `W-metatest-8`); `mutations.json` is parsed with default `json.loads`, so a duplicated key silently shrinks the battery, and no committed invariant test locks the table to the live sources (`W-metatest-7`, `T-metatest-2`). The advertised 93.63% coverage excludes the entire meta layer and is branch-blind (`W-metatest-9`); the controls CI job — the job the framework exists for — installs without the checkpoint extra (`W-metatest-11`); the incident reproduction can silently vanish from the suite behind a `pytest.skip` (`W-metatest-14`); DCP fixtures are monocultural (one shard, one tensor, declared metadata derived from the payload embedded in it — `W-metatest-11/12/13`). The feature asks converge on one point: give confidence a denominator — a mutation census that mutates every module or excuses it in writing (`F-metatest-2`), a real-manifest test producer (`F-metatest-3`/`F-metatest-8`), per-module coverage floors, harness-fidelity probes that mutate the test doubles themselves, and a machine-readable battery report so the public kill tally stops being maintained by hand (`F-metatest-5`).

### prov — provenance & manifest store (133)

The record plane repeats the gate plane's failure modes one level down. **Capture-side trust:** the git environment blocker (§3.5) has company — probe failure is stored as a measured zero and can roll up to CLEAN because the schema has no `UNKNOWN` (`W-prov-4`); secret values flow verbatim into finding strings and an append-only store that refuses overwrites (`W-prov-10`, `W-prov-9`); submodule contents are invisible while statuses claim CAPTURED/CLEAN (`W-prov-18`). **Load-side trust:** the load-boundary blocker (§3.6), plus self-claimed statuses that launder NOT_CAPTURED to CLEAN by editing two strings (`W-prov-16`), topology reconstruction with zero arithmetic validation (`W-prov-26`), and a stored fingerprint written on every save but never verified on load (`W-prov-23`). **Fingerprint semantics:** `entrypoint` is recorded but excluded from the semantic payload; captured environment makes fingerprints unstable across relaunches; `_derive_findings` has no vacuity branch; and `diff_paths=()` rolls up to CLEAN over zero examined paths — the `all([])` shape on the module's most doctrinal spot (`W-prov-29`). **Store mechanics:** a cross-process allocate→save check-then-act (`W-prov-3`), pid-only temp names plus `os.link` inode aliasing (`W-prov-5`), a read path that follows planted symlinks out of the root (`W-prov-17`), and no API to enumerate what the store holds (`F-prov-9`) — the coverage count that motivated the module cannot be computed.

### io — checkpoint readers (111)

The readers were built for well-formed bytes; three-quarters of this area is what happens when they meet anything else. **Hostile-input surface:** auditing a DCP checkpoint unpickles attacker-controlled `.metadata` with no restricted parser (`W-io-4`); shard and storage paths from untrusted metadata are opened with no containment (`W-io-5`, and the consolidated filing at `checkpoint/dcp_meta.py:473-487`); safetensors pre-flight manufactures storage claims from unvalidated JSON (`W-io-9`). **Taxonomy:** bare `RuntimeError` and library exceptions escape the `CheckpointError` contract on several read paths (`W-io-10`, `W-io-11`); the storage index silently absorbs duplicate and out-of-extent chunk records (`W-io-12`). **Adjudication minutiae beyond the NaN blocker:** all-zero-versus-near-zero returns CLOSE (`W-io-14`), `torch.equal` is dtype-agnostic so EXACT spans differing dtypes (`W-io-15`), bitwise-identical ±inf trips the self-check (`W-io-16`), and two shipped adjudicators duplicate magic thresholds and can disagree on the same record (`W-io-17`). **Mechanics:** block planning is width-unbounded and chunk-oblivious, with a false 0.5 GB memory bound and up to 64× decode amplification (`W-io-13`); non-tensor blob disagreement is invisible to `ParityReport.ok` (`W-io-20`); and manifest discovery trusts file placement — `load_manifest` adopts any manifest-shaped file in the checkpoint dir *or its parent* with no binding to the artifact (`W-io-8`). ## 6. What the audit could not see

After consolidation, four completeness critics were each given the entire surviving finding set plus the whole-tree API surface and asked for **classes** of problem the audit cannot see — not more instances of what it already found. They returned 49 classes (12 design, 10 adversary, 11 scale, 16 product), each with the argument for why the finding set cannot contain it by construction. Four of the 49 are graded BLOCKER by the critics. This is the most important section in this document, including — especially — where it indicts the audit itself.

### Design (12 classes)

The recurring shape is the framework enforcing on *adjudication* what it never imposed on *construction*. **Producer-side vacuity** (G-design-1, BLOCKER): `CheckpointGateContext.from_path` can enumerate zero of N tensors into a well-formed, empty world, and no coverage contract reaches that far upstream — a reproducible instance of the founding failure, one hop before every gate. **Enforcement is advisory** (G-design-2): artifacts carry no verified/unverified state on disk, so any consumer that never imports the library bypasses every gate; fail-closed currently means "raises inside a Python process that opted in." **No observer dimension** (G-design-3): a `GateResult` is one process's view, but the founding defect existed only in the *union* of eight ranks' truthful local views; nothing defines what aggregate a verdict binds. **No temporal axis** (G-design-4): every gate consumes a snapshot, so a metric flat for 472 steps — the estate's own second exhibit — is structurally inexpressible. Then the meta-classes: the "frozen contract" exists only as implementation consensus, with no numbered rules for controls, mutants, or findings to cite (G-design-5); every MUST_FIRE world was authored by the same hand as the detectors, with no externally sourced artifact corpus (G-design-6); no installed end-to-end journey has ever executed (G-design-7); the README's executable claims are never executed (G-design-8); no property-based testing stands on the parsers that consume hostile bytes (G-design-9); every atomicity and visibility claim rests on local POSIX semantics while the artifacts live on parallel filesystems (G-design-10); single-source parsing is celebrated where an independent-oracle policy should be (G-design-11); and the estate's defining constants are copy-pasted literals with two restatements already known not to reconcile (G-design-12).

### Adversary (10 classes)

The lens asked: who holds the enforcement keys? The answer is uncomfortable. **Enforcement-by-cooperation** (G-adversary-1, BLOCKER): the process being verified can reassign `Gate.ok`, mutate the registry, or swallow `GateBlocked` in one line — the audit's security lens was exclusively artifact→verifier and never verifyee→verifier; F-security-6 proposes process isolation in exactly the wrong direction. **Predicate vacuity** (G-adversary-2): `Tolerances(max_abs_diff=inf)` or a maximally raised threshold passes at genuinely nonzero coverage — the second `all([])`, one level inside the predicate. **No intrinsic payload health** (G-adversary-3): every content check is relational; a checkpoint of finite-shape, distinct-storage, all-NaN tensors passes all ten gates. **Most of the state is outside the perimeter** (G-adversary-4): optimizer slots, RNG, step counters, dataloader cursors — typically the majority of checkpoint bytes — have zero gates, so a checkpoint that resumes into a silently re-initialized optimizer passes everything. **Memorylessness** (G-adversary-5): a 0.9%-per-save deficit under a 1%-per-event tolerance compounds to worse-than-incident over eleven passes, each individually green. **Detectors are calibrated to the incident's literal signature** (G-adversary-6): one flipped mantissa bit per aliased copy defeats both aliasing gates at full byte volume — the controls prove the gates fire on *the* incident, not on its neighborhood. **The audit inherited the README's silence about the build and data stages** (G-adversary-7), two advertised lifecycle points with zero gates. And three self-referential classes — the audit's evidence chain is unverified (G-adversary-8), the ledger is an unqualified count (G-adversary-9), and installed bytes are unbound to audited bytes (G-adversary-10) — covered under the self-indictment below.

### Scale (11 classes)

The operationally fatal ones first. **A blocking verdict is indistinguishable from a crash** (G-scale-1): nothing defines what exit code a gated training job returns, so standard auto-requeue restarts it against the same corrupt artifact, forever — the dangerous-ops case for a per-save blocking gate. **Everything assumes single-node POSIX visibility** (G-scale-2): `os.link`/rename/fsync semantics and directory coherency are local-disk guarantees; the estate's checkpoints live on Lustre/GPFS-class storage where close-to-open and attribute caching change the system under the store. (Three lenses hit this class independently — design, scale, product — which reads as convergence, not padding.) **The deleter is unmodeled** (G-scale-3): retention reapers and async-save publication versus an in-flight gate have no contract; a gate can mint a PASS receipt over bytes a reaper has already unlinked. **The data plane has no lifecycle presence at all** (G-scale-4): no context type can express "the dataloader resumed correctly." **Doctrine 4 is unenforced at the contract** (G-scale-5): `Gate.ok()` can mint a PASS over `checked=3, expected=None` forever — missing denominators are rendered, not refused. **Format monoculture** (G-scale-6): every check-reading path is validated only against artifacts written by the same installed torch; no golden bytes separate "our reader changed" from "their format changed." **No fleet driver** (G-scale-7): the README's estate-census claims (200 of 205 export directories; 3,840 of 3,840 experts) cannot be regenerated by anything this repository ships. **No I/O civility contract** (G-scale-8) and **no cost governance** (G-scale-9): the verifier fights the training job for page cache and bandwidth unmeasured, and the battery's cost is mutants × full suite with no test selection — the property that decides whether checks still run in week 12. **Vacuous configuration** (G-scale-10): several `ClusterProfile` fields have no code path from field to finding, joining the `all([])` family one level above gates.

### Product (16 classes)

**No promotion discipline** (G-product-1, BLOCKER): a FAILED checkpoint is a perfectly ordinary directory; verdicts live in process memory; the incident's closing act — resume of the corrupt artifact — meets no structural obstacle for any consumer that doesn't opt in. **No shadow-rollout posture** (G-product-2, BLOCKER): the only documented mode is import-and-block, while at least one shipped gate has a catalogued healthy-layout misclassification (`W-ckpt-2`'s grammar findings) — so a new adopter's choice is "block a good save" or "uninstall," and alert fatigue on day one is exactly how verification frameworks get deleted. **No retryability signal** (G-product-3) twins G-scale-1.
