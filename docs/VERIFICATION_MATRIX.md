# Verification Matrix — FoundationScale

## The measurement that shapes everything

This matrix exists because of one measurement, taken before any of it was built, and the paragraphs below state that measurement in the past tense on purpose: #373 has since changed most of its numbers, and the next section says exactly which. The zeroes are kept rather than overwritten because they are the reason this matrix exists at all.

The instrument was a grep over `src/foundationscale` (excluding `rl/`), read against the code. The measurement: FoundationScale's training plane does NOT implement an inner loop. It builds a `transformers.Trainer` (`src/foundationscale/train/loop.py:2223`) out of `TrainingArguments`, from a kwargs dict (`src/foundationscale/train/loop.py:2103`) whose ENTIRE content was:

    output_dir, max_steps, per_device_train_batch_size, learning_rate,
    save_strategy, save_steps, seed, logging_steps, report_to,
    ddp_find_unused_parameters, (bf16|fp16) from cfg.precision, and
    save_safetensors when the installed transformers accepts it

TrainConfig's full field set was: model, dataset, output_dir, nodes, gpus_per_node, profile*, objective, precision, adapter*, max_steps, per_device_batch_size, learning_rate, save_interval, seed, dp/tp/pp/ep/cp, dry_run, launch_corpus.

The grep counted, at that time:

- `attn_implementation|flash_attention|sdpa` → 0 occurrences
- `torch.compile` → 0
- `get_scheduler|lr_scheduler|warmup` → 0
- `AdamW|Adafactor|SGD(` → 0
- `deepspeed|FSDP|fully_shard|ZeRO` → 2, both in `gates/` + `provenance/` (adjudicated/recorded, never built)
- `clip_grad|max_grad_norm` → 0

The consequence, and it is the whole point: every named axis — optimizer, CPU offload, DeepSpeed, gradient checkpointing, gradient accumulation, flash attention, LR schedule — was NOT absent from the RUN. HF Trainer supplies a default for each. It was absent from the DECLARATION. The run used `adamw_torch_fused`, accum=1, max_grad_norm=1.0, no recompute, linear LR with zero warmup, and whatever attention implementation the model config picks — and the manifest could not say so, because there was no config key to resolve and record.

Those six values are measured, not assumed: they are the `TrainingArguments` defaults read out of transformers 5.16.1. Stating the version is not pedantry — it is the whole shape of the problem. An undeclared axis takes its value from the installed engine, so the same FoundationScale config trains differently under a different transformers release, and no artifact of either run would record that anything changed. Note in particular that the optimizer default is the *fused* AdamW, not the reference one: T1-9 proposes to measure step time across optimizers, and it would be measuring against a fused baseline without ever saying so.

That is the #346 class at scale: unmeasured reads as green. It is why, when this matrix was written, 14 of its 33 rows were unrunnable.

## What #373 changed, and why the grep counts above no longer hold

#373 shipped tier 0, so **every count in the list above is now stale by design.** They are corrected here rather than edited in place because a matrix that quietly rewrites its own premise cannot be audited against the tree it described.

Re-measured on the same instrument, over the same scope, on the same day this section was written: `attn_implementation|flash_attention|sdpa` → 31 occurrences, `get_scheduler|lr_scheduler|warmup` → 26, `clip_grad|max_grad_norm` → 14, `deepspeed|FSDP|fully_shard|ZeRO` → 9 (the original two in `gates/` and `provenance/`, plus seven in `train/`), `AdamW|Adafactor|SGD(` → 3. Only `torch.compile` is still zero: nothing declares it, and it remains T1-15's business.

`TrainConfig` now carries nine tier-0 axes — `optimizer`, `gradient_accumulation_steps`, `max_grad_norm`, `gradient_checkpointing`, `attn_implementation`, `lr_scheduler_type`, `warmup_steps`, `sharding_strategy`, `cpu_optimizer_offload` — each resolved through `ConfigResolver` and recorded. Each is bound into the kwargs dict only when the operator declared it, so an undeclared axis still takes the engine default; what changed is that the ABSENCE is itself recorded, which is precisely the distinction the original measurement said no artifact could make.

Two of the nine are declarable without being executable, and the matrix says so rather than counting them as capability: `sharding_strategy=fsdp|zero3` and `cpu_optimizer_offload=true` REFUSE with 96 rather than accept a declaration this plane cannot honour. That is why T1-13 and T1-14 read REFUSED and not UNBLOCKED — an unrunnable arm is not the same fact as a missing one.

## Two tiers, and tier 0 is not optional

**Tier 0** (no GPU, blocks everything below): make each axis DECLARABLE and RECORDED. A knob that is exposed but unrecorded is worse than absent, because a run then makes a claim no artifact can check. Every tier-0 row is:

- (a) a TrainConfig field,
- (b) bound into the TrainingArguments kwargs,
- (c) resolved through ConfigResolver so `provenance/manifest.py` records key/value/source,
- (d) a control proving an off-declaration run REFUSES rather than silently training on the engine default.

**Tier 1** (GPU, a 4-GPU tray): one row per claim. Every row carries a CONTROL ARM — an arm that must come out DIFFERENT.

Tier 0 blocks tier 1 because a tier-1 row that toggles an undeclared axis measures nothing attributably: the run would train on the engine default either way, and no artifact could distinguish "the knob worked" from "the knob was never wired." Rows T1-9 through T1-14 each named the tier-0 row they waited on. #373 shipped all of those, so each of the six now names what released it: T1-9 through T1-12 have since RUN on a tray -- T1-9, T1-10 and T1-11 GREEN, all three re-taken at the same shipping commit so the three GREENs are attributable to one tree rather than to three ancestors, and T1-12 UNMEASURED because the flash_attn module is absent from the tray, which is the row refusing to report a two-arm result as its three-arm claim -- while T1-13 and T1-14 are REFUSED — the dependency shipped as a refusal, so their run arms have nothing to execute.

## Rows that cannot fail

The control-arm rule: a row with no arm that must come out differently is a row that cannot fail, and a row that cannot fail is not a measurement. This campaign has now produced several of those — #291, #294, and #372 — which is why every row in this matrix carries an explicit control arm, and why the JSON rendering of this matrix enforces, as a gate, that no `control_arm` field is empty.

## Ordering rule

T0-9 has left the queue, and it is the one row here that this matrix's own harness found RED and then saw fixed. The recording half was never wrong: an unversioned tree is recorded as such, with no commit invented for it, and a real checkout records the commit an independently read HEAD reports — so no row below ever inherited a misattribution. The loudness half was wrong, and measurably so: nothing outside the provenance module read code.status, so a run unpacked from a tarball exited clean without one of its lines saying it could not be attributed. It says so now, and a control run from a real checkout stays quiet, which is the part that keeps the line worth reading. T0-1..T0-8 are done: #373 shipped them, and their CPU-only proofs now run in the suite on every commit, so they no longer sit in this queue. What remains is tier 1, cheapest-first: T1-3, T1-22, T1-23 (minutes), then T1-4, T1-1, then the long ones (T1-5, T1-16). T1-21 has left the queue: the arm that #448 found unreachable on the Gemma-4 family is reachable now, and the row's tower-movement claim was measured on a tray against its own declared control -- the image arm moved every vision-tower module and the text-only arm moved none of them while still training its language anchor, so the null result is a measurement and not an arm that failed to run. T1-11 has left the queue: it ran on a tray and came back GREEN over three interleaved rounds, and the #408 false RED it was carrying did not reproduce — which is the useful part, because #408 was a harness defect and the only thing that can retire a harness defect is the harness being run again. ## Running the matrix, and how far the runner reaches

`validation_campaigns/verification_matrix/run_row.py` is what makes this ledger executable rather than descriptive: it drives a row's adjudicator, composes the argv from nothing but the flags that adjudicator's own `--help` declares, and writes a receipt that records the adjudicator's sha256, the claim's sha256, the interpreter and the platform — never a result back into `matrix.json`, because a runner that can edit its own ledger is not evidence. It was driven end-to-end on a tray for the first time at this commit, and two rows came back GREEN through it with receipts: the optimizer row over four arms and the accumulation row over two.

That pass also measured the runner itself, which is the part worth writing down. Of the ten rows that ship an adjudicator, the runner can drive six. The other four — the scaler row, the save-load parity row, the symlinked-shard row and the audio row — declare no `--out-dir`, so there is nowhere to hand them an output directory and the runner refuses them REFUSE rather than pretending. That is the honest code: the refusal names itself a defect in the instrument rather than an unmeasured property of the claim, and it is never a red. But it means the ledger's coverage and the runner's coverage are not the same number, and until those four adjudicators grow a run mode, "every adjudicated row" and "every row the runner can take" describe different sets (#472). The rows themselves are not unmeasured — the scaler, parity, symlink and audio rows were all measured by hand — so what is missing is reproducibility through one entry point, not evidence.

Wiring the text-movement row into the runner then exposed a second defect in the instrument, and this one was worse than a refusal because it was silent (#473). `--flag` collected its values into a dict keyed by the flag's name, so asking for `--flag adapter-target=q_proj --flag adapter-target=v_proj` composed `--adapter-target v_proj` alone: the first value was overwritten and nothing said so. Any adjudicator flag declared `action="append"` could therefore never receive more than one value through the harness, and the harness did not refuse — it ran a narrower experiment than the operator asked for and wrote a receipt that looked clean. The text-movement row adapts both `q_proj` and `v_proj`, so the first harness-driven pass of that row would have measured half the claim while reporting the whole one. The fix accumulates instead of overwriting and emits one flag occurrence per value; a single value composes the identical argv it always did, which is the part that has a control of its own. Both halves of the path are controlled separately, and reverting either one alone makes the self-test fire.

Running the row again with the flag fixed then found a third defect, and it is the most instructive of the three because every part of it worked (#474). The training ran, both arms completed, the adjudicator read the adapters and exited 0 — a real GREEN on real hardware — and the harness turned it into REFUSE 96 with the reason "exited 0 but wrote no arm files". The runner reads its observations from `<out-dir>/<row>_<arm>.json` and never from stdout, because a number that existed only in a scrollback is the thing it was built to stop; this adjudicator printed its payload to stdout and wrote only the per-arm training directories. So the seam discarded the measurement. That refusal is the runner behaving correctly — it saw no observations and declined to invent a verdict from prose — and it is also the whole cost of an undeclared convention: the adjudicator was written before it was wired to the runner, nothing in the repo checked that the two agreed, and the disagreement was invisible until a row was driven end to end. The adjudicator now writes an arm payload per arm, including for an arm that failed, since an absent file cannot be told apart from an arm that never ran. The control for it loads the shipped `run_row.py` and calls the shipped `collect_arms()` over a directory the adjudicator itself wrote, rather than re-stating the naming rule in a second place where it could drift again — renaming the payload makes it fire.

With all three fixed, the row was taken through the harness on a tray and came back GREEN with a receipt: `q_proj` and `v_proj` both adapted, the run arm moving 56 of 56 `lora_B` tensors with Frobenius norms from 0.008017275482416153 to 0.020371997728943825, the null arm leaving all 56 at a maximum of exactly 0.0, under Python 3.11.15 on aarch64. Those numbers reproduce the ones taken by hand, by a different route, with the adjudicator's own sha256 in the receipt. The general lesson is the one worth keeping: all three defects were in the instrument rather than in any claim, none of them was visible from reading the code, and each surfaced the first time something was actually run through it end to end.

Asking how far that lesson generalised found a fourth defect in the runner itself, and it is the same trap one level down (#475). Rule 5 refuses an exit of 0 or 5 with ZERO arm files, because a verdict with no observations behind it is `all([])`. It did not refuse an arm file that parsed, was an object, and could not say whether the arm had been measured. In the limit such a payload lifts nothing at all and the receipt reads `arms: {"run": {}}` beside `verdict: green` — an empty MEMBER where rule 5 only ever guarded against an empty SET. The two real payloads that hit this are less stark than that and worse for it: both carry evidence — the accumulation row's arms lift telemetry and a loss curve, the gradient-checkpointing row's lift telemetry, excerpts and a launcher exit code — so the arm entries are populated and the receipt reads as substantiated, while neither arm anywhere states that it was measured. An empty entry would at least have looked wrong. Reverting the fix makes the runner exit 0 on exactly that input and print "claim upheld; 1 arm(s) measured", which is the receipt asserting a measurement that is not in it. Only `status` is required and the other five keys stay optional on purpose: the evidence keys are genuinely per-row — a row whose evidence is adapter norms has no loss curve — whereas `status` is not evidence but the arm's identity, the one thing a receipt cannot be silent about. The control writes a payload that DOES carry telemetry, so a weaker fix that merely demanded a non-empty dict would not satisfy it.

That defect was found by reviewing a second adjudicator rather than by running one, and the review raised a question nobody had asked: how many of the rows that declare an adjudicator can actually carry a measurement through the seam today? The first answer was a reading of the source, and it was wrong. It counted the adjudicators that write per-arm payload files by pattern-matching how each one builds a path, concluded four, and predicted that the gradient-checkpointing row wrote none; driven through the runner, that row exited 0 and wrote nine. A pattern that can misread one row can misread any of them, so the remaining rows were run rather than read, and all ten now have a measured answer instead of an inferred one (#476).

Five carry a payload through the seam — the optimizer, accumulation, gradient-checkpointing, attention-backend and text-movement rows — writing four, two, nine, fourteen and two arm files. Four refuse before execution for the #472 reason above, declaring no `--out-dir` and so having nowhere to be handed one. The tenth, the vision-tower row, is reachable and refuses on its own terms: the model, the two corpora and the two module patterns it needs are estate facts with no defensible default, so it declines to invent them. That last outcome is the adjudicator working correctly rather than a defect, and the earlier reading had no way to express it — which is the particular way a count of files misleads, because it cannot tell an instrument that cannot be reached apart from one that reaches the claim and honestly declines.

Of the five that do carry payloads, three say whether their arms were measured and two do not, so #475 converts two standing harness greens into refusals: the accumulation row and the gradient-checkpointing row both exited 0, and neither receipt could substantiate it. The hand-taken measurements behind those two rows are untouched and still stand; what no longer stands is the claim that the harness reproduced them. The cause is not carelessness in two files but a contract that was never written down. The five payload writers agree on almost nothing: three write `status`, one writes `refused` in its place and one writes neither; three write `launcher_exit_code`, one writes `launcher_exit` and one writes no exit key at all; three write `loss_curve`, one writes `loss_series` and one writes neither. `ARM_SCALAR_KEYS` was a list of keys the runner happens to lift, never a contract published to anyone writing a payload, so each adjudicator invented its own spelling and none of them was wrong to. The fix that matches that cause is a shared writer exported beside `collect_arms()` so the naming rule lives in one place; widening the lift list to accept each new spelling would bless the divergence and guarantee a sixth. The gap remains the number that matters: the matrix declares an adjudicator for ten rows, and the shipped harness can presently carry a substantiated receipt from three of them — two green and one an honest UNMEASURED.
