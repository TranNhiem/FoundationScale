### 1.1 The reward modules (detail)

**59** files define `reward_m1m4`, collapsing to **8** md5s **[V·post]** — of which **23 are live-tree copies (the shadowing surface, unchanged) and 36 are `results/<run>/repro/code_snapshot/` provenance copies**, i.e. the extra files are the audit trail, not more shadowing. (The earlier 24/6 count inherited `fs_inventory.json`'s extension filter — 9,905 indexed entries against **19,912** real `.py` files — the same filter that caused the κ miss. F7 again, on this document's own method.) They implement 4 distinct gold policies [V]: **(P1)** `sdpo`: gold short-circuits to 1.0 (2 copies, md5 `8c5972bd`); **(P2)** `gspo`: gold is a post-judge *floor to the family pass threshold* (default 0.6, **not** 1.0; 19 copies, 18 byte-identical plus a docstring-only diff); **(P3)** `sdpo_facts`: opt-in `OMNI_GOLD_MISS_IS_BAD` forces 0 on gold miss (1 copy; **defaults off and no launcher exports it**, so only 3 distinct default behaviours); **(P4)** `mb/sdpo_gemma4`: deterministic grader as pre-judge primary with hard 1.0/0.0/abstain (1 copy). Note the name trap: `accel/sdpo_gemma4` is gspo-family; `mb/sdpo_gemma4` is grader-primary.

Two mechanisms make this structurally toxic rather than merely messy. (a) The module is imported by bare name from the CWD (`from omni_sdpo_reward import build_reward_fn`, `run_gspo.py:40`), so **the objective RL optimises is selected by which directory you `cd` into**, with no version marker. (b) Both policy flags are read at *module import time* — setting them after import silently no-ops, and a dead duplicate `_GOLD_MISS_IS_BAD` at `mb/sdpo_gemma4:787` shows the copy-paste-patch workflow already generating unreachable code [V].

**S19 is the most important row in this table and it is not about the training code.** It is a fourth instance of F3 — the audit's central thesis that *the dangerous failures are the ones that report success* — found inside the tool built specifically to catch that class, by the one technique this document keeps insisting on. Every earlier row here was discovered forensically, weeks or months after the damage. S19 was caught in minutes, by a negative control, before its result was believed. The difference between those two outcomes is the entire argument for the gate catalogue: not that careful engineers avoid this bug — the engineer who wrote the detector for it wrote it anyway — but that a cheap adversarial control catches it every time.

**S20 settles the question of whether S19 was a fluke.** The obvious objection to S19 is
that a throwaway audit script is not production code, and a real system would not ship
an `all([])`. S20 is that same bug, in the training loop, in the checked-in objective,
guarding the estate's only semantic invariant — and it is subtler than S19 in the one way
that matters: the metrics are not merely absent, they are **fabricated to look healthy**.
`_zero_metrics` does not return an empty dict for a microbatch with nothing to supervise;
it returns `seq_ratio_mean=1.0, clip_fraction=0.0`, which are exactly the values a correct
step produces. The flag that would have revealed it, `no_supervision`, is in the same dict,
one key away, and the checker does not read it. Two independent instances of one bug class,
in code written by different people for different purposes, is not a fluke; it is the
default outcome of writing checks that ask *did anything go wrong* instead of *how much did
I actually examine*.

from a captured one. One repo has **35 bundles against 119 result dirs (29%)**; the other
has **77 result dirs and zero bundles (0%)**. The ledger records **62 launches against 35

## 3. Blast-radius accounting: the aliased base

Census of all 20 Gemma4-MoE `run_config.yaml` files [A]: **9 runs trained from the aliased base `gemma-4-26b-it`**.

- **2 full-FT runs** (`official_fullft_16k`, `muon_fullft_16k`): 20 checkpoints, all carrying the bug signature (5.73 GB expert bytes, 960 indexed keys). These checkpoints are **invalid**; quarantine stands.
- **7 LoRA runs** (`lora_matched_16k`, `lora_recompA_16k`, `muon_lora_16k_lr5e5`, `muonperhead_lora_16k_lr5e5`, `muon_lora_16k_UNSTABLE`, `lora_fullrecomp_DIVERGED`, `probe_lora_4096`, plus `probe_lora_16384` at EP=4). These are the more insidious case: **LoRA adapter checkpoints are structurally clean — 0 expert bytes — and pass every structural check while sitting on a frozen base that was 87.5% wrong.** Nothing in the artefact says so.
- The other 11 runs use `-expertfix` bases and all measure 45.70 GB / 0 indexed keys.

What is known about downstream impact [V, adjudicator-closed]: the aliased runs fed a **published optimizer comparison** (`CHECKPOINT_INVENTORY.md`, `BENCHMARK_GUIDE.md`), a *methodological* conclusion in `MUON_RUNBOOK.md`, and a **model decision** — 10 merged HF exports declared ready to serve. Retraction hygiene in-repo is banner-based; the wrong numbers remain present and greppable (F7).

The correction is not merely that the old numbers are invalid — **the conclusion inverted** (S18). A structural bug silently reversed the outcome of a controlled experiment: Muon's measured edge was an edge *on a crippled model* (a 16-expert model replicated 8×). The LoRA arm's clean, matched replacement already exists on disk (jobs J09/J10), so adopting the reversed result costs **zero GPU time**. Genuinely requiring GPU time: Muon-vs-AdamW at full-FT (no Muon full-FT v2 exists), `muonperhead` at 16K, and the `lora_recompA` LR-stability claim.

Both of the things this section listed as unknown are now **closed [V·post]**, and closed for free: the expert fix is numerically correct (3,840/3,840 experts bitwise identical across all 30 layers, positive controls firing at 128 and 112), and no exported MoE artefact contains a permuted expert axis (`argmax == identity` everywhere checked, min margin 0.804). Neither needed a GPU — the DCP `.metadata` offset table makes individual tensor chunks byte-range-readable. **One unknown replaces them, and it is not reducible to bytes:** no exported artefact has ever been run. D8.3's parity probe is now the *only* unscheduled correctness gate, and its scope narrows from "is the conversion faithful" (answered: yes) to "does the served model behave like the trained one" (open).

## 4. Reproducibility assessment

**A past run cannot, in general, be reproduced from committed artefacts.** The blockers, enumerated:

1. **Code.** `omni-accel` — the more active repo (3,010 files / 681,440 LOC) — **is not a git repository at all**. Its sibling has HEAD `5744a25`, 7 commits in 90 days, and **892 dirty files**. Which code a run executed is not recorded anywhere; per §1.1, which *objective* it executed is not recoverable from the code tree at all.
2. **Configuration.** 166 distinct environment variables (37 `OMNI_*`, 26 `SDPO_*`, …), ~247 launchers carrying the actual run configuration, only 3–4 real recipe names, ~20 cloned judge-registry YAMLs hardcoding point-in-time hostnames. Only ~1 of ~97 checkpoint-exercise... — rather: run_config.yaml dumps exist but are unreliable (`muon.py:214` mutates `config.optimizer` pre-dump) [V].
3. **Environment as hidden objective.** Two reward-semantics flags are import-time env reads (S17, D5); a hand-exported variable governed ≥12 runs with zero on-disk trace.
4. **Snapshot mechanism.** `code_snapshots/` full-tree copies freeze stale node endpoints and are re-serialized without comments — destroying the incident annotations that encode validation knowledge.
5. **Runtime identity.** No seed capture safe against the watchdog's mid-run seed mutation; the trainable-parameter partition appears in no config dump in any log (even for the ~24 B3 jobs that ran); no content hash of the reward module is stamped anywhere.

**The accidental provenance record.** What the system has instead of designed provenance is the judge-audit JSONL: every RL launcher passes `--judge_audit_path`, and the per-sample `decided_by` vocabulary uniquely fingerprints the gold policy class (`gold_fastpath`→P1, `gold+judge`→P2, `gold_miss`→P3, `gold_rule_pass|fail`→P4) [V]. This recovers the objective *class* for essentially every logged run — which is how S16 and S17 were found at all. Its limits must be stated: it resolves P1–P4, not the md5 (several backup variants share a class; two share an mtime with different content, so the backup chain is not even a total order) [U]; it lives in `.jsonl` files the audit's own inventory excluded; and its most-load-bearing report (`shadow_grade`) is stdout-only. FoundationScale replaces this entirely with P3 (resolved config + code/data hashes + seed + topology + objective version per run); until then, the audit logs are the only objective-provenance source and must be preserved and indexed as such.

## 5. Limitations as a framework foundation

1. **Scale beyond 32 GPUs is unvalidated.** Measured ceiling: 8 nodes / 32 GPUs / EP=32 [M]. The only >8-node scripts in the tree are vendored NVIDIA examples for GLM-4.5V and Qwen3.5-VL with **no Omni logs behind them** — they are false evidence of scale and should be quarantined before they mislead another reviewer (they already produced one false negative). The 100+-node goal is unmeasured by three orders of magnitude, and the DP1-default NCCL hang (S12) is an *unresolved* bug on the path to it.
2. **No pretraining data plane.** 0 of 1,344 first-party `.py` touch `GPTDataset`/`BlendedMegatronDatasetBuilder`/mmap corpora; 0 of 532 `.sh` reference `.bin`/`.idx`/`--data-path`/`blend`; no tokenizer training [V]. `pretraining_data/` contains SFT jsonl, not a pretraining corpus. The engine, however, is present and proven: `accel/train_resume_test_e4b.py` drove the real `megatron.bridge.training.pretrain` with random init and mock data end-to-end (12 steps, 7.52B params, Slurm job J01). D12: build the data plane, reuse the engine, and **guard the capability inventory** — mock-data smoke runs produce checkpoints indistinguishable on disk from real ones.
3. **The VLM lower ladder has never executed.** Only B3 (visual instruction tuning) has real runtime evidence (~24 jobs, iter_0002400). B1 has 0 logs/checkpoints — it needs no new code (freeze primitives exist [V], expressible as a recipe + dotted overrides) but it needs a corpus, and the documented one is empty (`Taiwan-formosa-VLM-caption-V1/data/` = 0 files; `Formosa-Vision/data/` has 23 unreferenced parquet shards). B2 has no interleaved loader and **no full-document loss path anywhere** — its blocker is the objective, not the plumbing. B4 ran a 5-iteration smoke (2026-06-24) whose checkpoint dir is empty, with reward computed on rank 0 (DP=1 only) and the hardcoded freeze bug (S15). Any roadmap treating B1–B4 as "mostly built" is mis-scoped by three of four stages.
4. **A4 is ~60% real; the missing 40% is the word "multi".** Present and running: on-policy self-sampling, refit with staleness p99 tripwires, one genuinely frozen co-resident teacher, the per-token clipped α-divergence objective (4,169 logged steps). Categorically absent: N>1 teacher residency (`--anchor_ckpt` is a single optional string), content-based per-rollout teacher routing, and any weight fusion (zero hits for slerp/TIES/task-arithmetic/DARE across 9,905 files) [V]. **Memory, not code, is the wall**: N co-resident 26B teachers do not fit, so the one genuinely new engineering item is a remote-logprob teacher service — which is itself an argument for reusing the (forked, §1) judge registry/pool substrate rather than the co-resident anchor substrate, after adjudicating the two variants.
5. **Portable execution barely exists.** The single-GPU path is real (six launchers default `TRAIN_GPUS=1`, 14 logs print `DP=1 TP=1 EP=1`, two reach step 300) but it is *Megatron degenerated to one rank*, it requests a full 4-GPU tray and self-restricts via `CUDA_VISIBLE_DEVICES` (which is why directive-based censuses miss it), and it has only ever run from pretrained checkpoints — **there is no proven 1-GPU from-scratch path**. Off-Slurm production is a genuine path (31 `offslurm_*` scripts, current production per TRAYS_IN_USE.txt) but a bolt-on: the command is string-grepped from `DRYRUN=1` output, supported by exactly **1 of ~240 launchers**. Everything is Megatron (748 of 2,888 non-vendored `.py` import it; zero TRL/HF-Trainer/FSDP entrypoints), so D2's FSDP2 backend remains a measured-decision gate, not a rescue.
6. **No semantic verification anywhere** (§2). Weight-level parity now holds on 200/205 exports [V·post], but **zero exports have ever been asked to generate**; no run records its frozen partition; no run records its reward version. This is the framework's foundational gap, and it is independent of scale. The correction sharpens it rather than shrinking it: the program can now prove its bytes are right and still cannot prove its models work.
